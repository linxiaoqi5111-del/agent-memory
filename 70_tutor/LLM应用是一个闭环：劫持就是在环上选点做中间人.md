# LLM 应用是一个闭环：劫持就是在环上选点做中间人

## 一句话先懂
- 任何 LLM 应用都是 `ask → compose（攒请求）→ send → receive → act` 的闭环；因为"智能"住在你不拥有的远端模型里，请求必然要跨过一条你自己机器上能碰到的边界——**谁能在那条边界上"看见并改写"这段请求，谁就夺走了控制权。这就是对 LLM 请求做中间人（MITM，Man-In-The-Middle 中间人攻击）。**

## 大白话解释
- 你的 App 要用 AI，但 AI 不在你电脑上，在人家服务器上。所以每次用 AI，都是"你 App 写一段话 → 寄出去 → 人家算完寄回来 → App 照着做"。
- 你在"寄出去"和"寄回来"中间摆一张桌子（=代理），所有信都得先过这张桌子。坐在桌子后面：想偷看能偷看、想改内容能改、想改寄给别人也能改。
- **上行（发出去时）能干两件事**：改地址（换模型/换供应商）、改内容（换 system prompt、改工具定义、去名）。
- **下行（发回来时）能干两件事**：改结果（过滤/改写/转协议）、偷内容（抄一份留底=蒸馏）。
- 结论：不是"发出去还是发回来二选一"——代理坐在环的中间点，**上行下行都归它管**，"在哪劫持"是按目的选的开关，不是限制。

## 技术映射
- 四个拦截层次不是四种技术，而是同一条请求路径上、**从"厂商没设防"到"厂商把你当敌人"的一条光谱**；排序的唯一变量是"厂商假设你的机器有多不可信"：
  1. **配置/环境变量层（最易）**：厂商留了口子，直接改。例：Claude Code 认 `ANTHROPIC_BASE_URL`；Cursor 可填自定义 OpenAI 兼容 `Base URL + Key`。cc switch 活在这层。
  2. **进程/参数层**：客户端是你机器上的进程 → hook `child_process.spawn`、改启动参数（把 `--api_server_url` 改成本地代理）。dao-proxy 走这层。
  3. **网络层 MITM（最通用）**：不碰 App，占领它必经的"邮局"——本地代理 + 自签证书解 TLS。卡点：证书固定（cert pinning，客户端只认真身份服务器的证书）、mTLS、gRPC/protobuf 私有帧（dao-proxy 满屏注释就是在啃 Cascade 的 gRPC 帧）。
  4. **二进制层（最难）**：协议加密/混淆/WASM → 反汇编、hook native 函数、脱壳。
- 理性策略：永远从①试起，能在浅层解决就不下沉。逆向通则=最小代价路径。

## 术语对照
- `MITM（Man-In-The-Middle，中间人）`：坐在通信双方中间，能观测并改写在途数据。
- `cert pinning（证书固定）`：客户端只信任内置的特定证书，普通自签证书代理会被它拒绝。
- `harness（壳/骨架）`：agent 的工具契约、编辑器集成、任务循环等非模型部分。
- `BYOK（Bring Your Own Key，自带密钥）`：用自己的第三方模型密钥替换官方后端。

## 本轮场景对照
- dao-proxy-pro = 把 Devin/Windsurf 当 harness，用层②/③劫持推理管道：上行换模型（路由到 DeepSeek/GLM 等）+ 换 system prompt（invert《老子》/严格替换/去名），下行做协议转换与错误帧收尾。
- 用户此前对 Knevo"蒸馏对话" = 偏被动，主要在下行读，不改东西。
- 两者本质不同：蒸馏=观测（读），harness 劫持=观测+改写（读+写），后者门槛与收益高一个量级。

## 边界与反例
- 劫持推理管道 **≠ 偷到模型**：你拿到的永远只是请求/响应控制权，不是权重；所以 dao-proxy 也得自己接第三方模型。
- **改写能力 ≠ 绕过计费/鉴权**：改的是"发去哪、发什么"，鉴权 token 通常仍在厂商手里；绕鉴权是另一场仗，也是 ToS/法律红线。
- 层级越深 **≠ 越高级**：能用层①解决还去做层④是工程灾难。
- 换模型成功的真正难点不在"改地址"，在**协议 + 工具契约要对得上**（对不上 agent 直接散架）。

## 可复用检查清单
- 想接管某封闭 LLM 产品，先问：明文请求在我机器上的哪一层出现？厂商在那一层设了什么防（env 口子 / pinning / 私有协议 / 混淆）？
- 从层①往下试，不要一上来 MITM。
- 换后端前先确认：目标模型协议能不能对上？工具 schema 认不认？
- 判断"读 vs 写"：只要数据就监听下行；要控制行为就改上行。

## 自测题
- 有个手机 App，聊天走后端 LLM，你用抓包代理却啥也看不到（连不上/报错）。这最可能是厂商在哪一层设了防？你会先试哪个突破口？

- 抓包代理拦不到，说明请求没停在"网络层可解"的地方——最可能是层③被 **cert pinning / mTLS** 挡住（App 拒绝走你的代理证书），也可能协议被加密到层④。
- 突破口顺序：先看有没有层①口子（App 设置/配置文件里的 base_url）；没有就上层②/③——用 Frida 等工具 hook 客户端绕过 pinning，让流量重新可解；实在不行才下沉到层④反汇编。核心判断依据：能在越浅的层解决越省事，pinning 是横在层③的典型墙。

## 跨领域同构
- 经典 MITM 威胁模型，只是对象从"HTTPS 流量"换成"LLM 请求"；安全界的 cert pinning / mTLS / 代码混淆正是厂商用来逐层抬高破解难度的防御手段——攻防一体两面（面试常考）。
