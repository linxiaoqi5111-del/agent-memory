# 数据量不是完成度：可验证知识闭环

## 一句话先懂

资料进入系统，只相当于快递被扫过码；只有它身份明确、关系有证据、时间可回放、结果有回执，并且最终能服务真实问题，才算成为可用知识。

## 大白话解释

把知识系统想成一座仓库。

仓库今天扫描了一千个包裹，只能说明一千个包裹经过了扫码枪。它没有说明：

- 哪些已经验收并上架；
- 哪些因包装不合格被拒绝；
- 哪些缺少货架或商品编号，暂时无法入库；
- 哪些仍在等待人工判断；
- 每个包裹以后能否查到来源、时间和处理结果。

所以，`processed（已处理）` 不等于 `applied（已应用）`，更不等于“知识已经完整”。真正的流程闭环，是每个候选都有一个可解释、可追溯的终态，而不是所有候选都被强行写进正式知识库。

这也意味着两个指标必须分开：

1. **执行是否闭环**：有没有候选被静默丢失，每条是否都有明确回执；
2. **知识覆盖是否完整**：目标事实、概念和关系是否已经补齐。

一批任务可以已经执行闭环，但仍有待补的知识缺口。

`Graph RAG（Graph Retrieval-Augmented Generation，图检索增强生成）` 像仓库里的高速叉车：它会沿关系快速搬运相邻知识。如果货号重复、关系错误、时间混乱，叉车不会修复这些问题，只会更快地把错误送到回答端。

## 技术映射

一条知识要形成可验证闭环，至少需要五层契约：

| 层 | 要回答的问题 | 最小要求 |
|---|---|---|
| 事实 | 到底发生了什么？ | 内容可核验，能回溯原始来源 |
| 概念 | 这件事属于哪个标准对象？ | 解析到 `canonical concept（规范概念）`，避免同义词重复建节点 |
| 关系 | 对象之间怎样连接？ | 使用 `typed relation（带类型关系）`，记录方向、含义和证据 |
| 时间 | 这条信息何时描述、何时可知？ | 记录报告期以及 `PIT（Point-in-Time，时点可得性）` |
| 回执 | 处理最终发生了什么？ | 保存 `receipt（处理回执）`，区分成功、拒绝、待审和缺少前置关系 |

候选状态可以按实际系统命名，但语义必须明确。例如：

```text
processed（已处理）       已尝试执行
applied（已应用）         已进入正式知识
review（待人工审核）      无法自动裁决
rejected（已拒绝）        不符合准入规则
no_exposure（缺少暴露关系） 缺少必要关系，原因与后续条件已记录
```

关键不是状态名称，而是不能出现 `silent skip（静默跳过）`：任务看起来跑完了，候选却没有留下任何可审计结果。

## 术语对照

- `canonical concept（规范概念）`：系统中代表某个概念的唯一标准身份；其他近似名称作为别名指向它。
- `typed relation（带类型关系）`：不仅记录“A 与 B 有连接”，还说明供应、竞争、隶属或暴露等关系语义与方向。
- `PIT（Point-in-Time，时点可得性）`：某条信息在历史上的哪个时间点已经可以被当时的使用者知道。
- `receipt（处理回执）`：记录一次处理的输入、结果、原因和终态，供追踪与审计。
- `ontology（本体 / 概念体系）`：规定系统中有哪些节点类型、概念层级和关系类型的结构规则。
- `Graph RAG（图检索增强生成）`：先定位图中的实体或概念，再沿有意义的关系扩展上下文的检索增强生成方式。

## 本轮场景对照

合理的推进方式不是把全库按“全部采集 → 全部概念 → 全部证据 → 全部链接 → 最后图检索”串行做完，而是让两条线并行：

1. **广覆盖采集**持续提供原料；
2. **高价值主题纵向切片**先证明知识产品可用。

一个主题的纵向切片要依次跑通：

```text
定义概念
→ 合并别名并确定上位概念
→ 建立产业链与公司关系
→ 绑定证据和时点
→ 建立链接
→ 用真实问题做检索评测
```

这相当于先完整试生产一件产品，而不是先把所有车间都扩建完。跑通少量高价值主题后，才知道瓶颈究竟在采集、概念治理、关系写入还是检索；验证有效后再扩大规模。

`Graph RAG（图检索增强生成）` 应放在这条闭环之后，并与关键词检索、混合检索等基线做对照实验。图扩展带来真实检索收益时才值得采用，不能因为节点和链接数量增加，就默认系统已经更智能。

## 边界与反例

- 这不是反对广覆盖采集。没有持续原料供给，纵向切片也无法扩展。
- 这不是要求所有小任务都设计复杂状态机。原子、可直接验证且失败可见的任务可以保持简单。
- 执行闭环不代表知识覆盖完整。缺口有明确终态，只说明它没有被静默丢失。
- 知识覆盖完整也不代表回答质量可靠。仍要用真实问题评测召回、排序和证据链。
- 不是每个新词都应成为新概念。技术参数、报告标题、泛化标签和已有别名若直接进入 `ontology（本体 / 概念体系）`，会让图检索放大噪音。

## 可复用检查清单

面对任何“已经处理很多数据”的项目，先问：

1. 每个候选是否都有明确终态，还是存在静默跳过？
2. 成功处理、正式应用、拒绝、待审和缺少前置条件是否被分别统计？
3. 每条知识能否回溯来源、报告期和时点可得性？
4. 新概念是否经过别名、上位概念、节点类型和来源检查？
5. 关系是否有类型、方向和证据，而不只是普通链接？
6. 是否已经用一个高价值主题跑通端到端闭环？
7. 新检索架构是否通过真实问题和基线对照证明收益？

## 自测题

某项目处理了 1,000 条候选：950 条已应用；另外 50 条缺少必要关系，但每条都有明确原因、重试条件、来源、时点和终态回执。这批任务应该怎样判断？

<details>
<summary>参考答案</summary>

本轮执行已经闭环，因为所有候选都有可解释、可追溯的终态；但知识覆盖仍有 50 条缺口，需要后续补齐。不能把“执行闭环”和“覆盖完整”混成一个完成指标。

## 跨领域同构

- **快递仓储**：扫码、验收、上架和可配送是不同状态。
- **支付订单**：扣款失败也可以是已闭环终态；没有回执的处理中订单才是流程风险。
- **消息队列**：收到消息不等于处理成功，需要确认、重试或死信结果。
- **产品开发**：先用一个纵向切片跑通用户价值，再扩建所有横向基础设施。
- **制造质检**：产量只说明吞吐，良率、缺陷原因和追溯链才说明产品是否可用。
