# 中间人位置的双面性：劫持与 AI Gateway 同源

## 一句话先懂
- 在 LLM 请求闭环上"摆一张桌子（代理）"这个位置，**恶用就是劫持（dao-proxy），善用就是 AI Gateway（LiteLLM/OpenRouter/Helicone 等）**——同一个位置、同一个原理，缓存/观测/记账/限流/故障切换全都是"因为所有请求必过这张桌子"才白捡到的能力。

## 大白话解释
- 你的 App 本来直接把请求寄给模型；改成先寄到你摆的桌子，桌子再替你转出去。就多了个中间站。
- 因为"信必过桌子"，坐桌子后面的人顺手能做一堆正经事：
  - **缓存（省钱省时间）**：桌子把"问过的问题和答案"记在小本子上，一模一样的问题再来就直接翻本子，不寄出去了。
  - **观测（看清每次调用）**：每过一封信就在登记簿记一行——几点、哪个模型、进出多少字、多久、成没成、哪个用户、多少钱。
  - **记账**：登记簿里的 token 数 × 各模型单价 → 按用户/按 key 一加就知道谁花了多少。
  - **限流**：给每个 key 记个计数器，超额当场拒收。
  - **故障切换**：这家挂了自动改发另一家。
- 卖 LiteLLM/OpenRouter 这些的，卖的不是模型，是"那张桌子"本身。

## 技术映射
- **精确缓存**：把整条请求（模型名+对话+参数）算哈希当钥匙，答案存 Redis/内存；来一条先查，命中直接返回，没命中才真调用并写回。
- **语义缓存**：把问题转成向量，措辞不同但语义相近也命中——但答案不该复用的场景（带实时数据）不能开。
- **观测/记账**：代理是唯一必经点（chokepoint），天然看到 token/延迟/费用/成败，写进 DB，再用看板画图；**不用改 App、不用碰模型，光靠"坐中间"白捡数据**。
- **故障切换/负载均衡**：桌子维护一个 provider 列表，出错/超时就试下一个；多 key 轮询。
- **分级路由（真正省钱的杠杆）**：简单请求发便宜模型，复杂的才发贵的。
- **LiteLLM**：不是"小模型"！它一个模型都不含，是把 100+ 家接口统一成一个标准接口的开源"转接头"（Lite=轻量胶水层，LLM=接 LLM 用的工具）。

## 术语对照
- `AI Gateway（AI 网关）`：坐在 App 与模型之间、你自愿接入的代理，做统一接入/缓存/观测/路由。
- `chokepoint（必经点/咽喉点）`：所有流量都要经过的单点，因此能在此集中管控与采集。
- `prompt caching（提示缓存）`：把不变的请求前缀在上游模型侧缓存复用（服务端能力，本地代理造不出）。
- `LiteLLM`：开源统一 LLM 接入层/代理，非模型。

## 本轮场景对照
- 用户直连 kfcoding.codes（第三方中转）用 Claude Code，遇到 502 且被偷塞 ~6800 token。
- 结论：用户可以在自己这侧摆桌子（本机 LiteLLM），但**缓存对 agent 流量几乎不省钱**——Claude Code 每轮上下文都在变，两次请求极少完全相同，精确缓存不命中；能真省钱的 prompt caching 在服务端，本地造不出。
- 对用户最实在的收益是：**故障切换（治 502）+ 观测记账（看清 6800 底噪一个月吃多少）+ 分级路由**，而不是缓存。

## 边界与反例
- 缓存只对"重复问法多"的场景香（批量翻译/分类/FAQ）；agent 类流量（上下文不断变长）基本不命中。
- 语义缓存对"带实时数据/需要新鲜答案"的请求是坑，会返回过期答案。
- 本地代理造不出上游的 prompt caching；也删不掉别人服务端的注入（如 kfcoding 那 6800 token）。
- 桌子是双刃：善用=Gateway，未经同意版=劫持（dao-proxy）；位置相同，合规不同。

## 可复用检查清单
- 想省钱先分清流量类型：重复问法多→上缓存；agent/上下文常变→别指望缓存，改用分级路由。
- 想稳先做故障切换（多 provider/多 key），这是中转不稳时最实在的一条。
- 想看清成本，直接在代理侧开观测记账，不用改业务代码。
- 别自己造轮子：LiteLLM/OpenRouter/Cloudflare AI Gateway 就是现成的桌子。

## 自测题
- 你想给一个"每天跑几千次、问法高度重复的批量分类"服务省钱，另一个是"多轮 coding agent"。哪个适合上缓存？为什么另一个不适合，该改用什么？

<details>
<summary>参考答案</summary>

- 批量分类适合上缓存：问法重复度高，精确/语义缓存命中率高，直接省调用。
- coding agent 不适合：每轮上下文都在变，几乎没有两次请求完全相同，缓存命中率极低；应改用**分级路由**（简单步骤发便宜模型、复杂步骤发贵模型）+ 故障切换，靠"选便宜活"而非"复用旧答案"来省钱。

</details>

## 跨领域同构
- 与 CDN/HTTP 反向代理同构：反代也是靠"必经点"做缓存、限流、观测、故障转移。AI Gateway 就是"面向 LLM 请求的反向代理"。
